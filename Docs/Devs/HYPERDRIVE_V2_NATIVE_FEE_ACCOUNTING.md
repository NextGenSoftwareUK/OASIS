## Original signing-authority trust boundary (2026-10-17)

`UsageNativePreparation.SigningAuthority` is an immutable public-context record, not a secret-key store or a proof supplied by an API user. Scheme is at most64characters, canonical base64 evidence at most65536characters; it contributes to the existing signed-evidence operation budget. Existing preparation and priced callback signatures are retained; additive overloads take context from the trusted adapter closure, never from native callback JSON. JSON authority injection is ignored. Mongo reload and central reader snapshots retain the original value.

- **Hedera:** `hedera-payer-public-key-v1` contains UTF-8 public key bytes. The admission caller must independently authorize this key for the payer, as before; an SDK signature proves possession, not payer-account authorization. Native storage supplies configured operator context. Both escrow stages retain it. Original-fee recovery re-verifies signatures and per-node SHA384 payload hashes, refuses missing context and refuses replacement keys. It does not query today's account key or reconstruct lost historical authority.
- **TRON:** `tron-account-permissions-v1` contains official protobuf `Account` limited to Address, OwnerPermission and ActivePermission. The shared client verifies configured genesis/solidified account, validates original signed operation permissions, then persists this minimal context before broadcast. No balance/account-name/private key is retained. Self-contained recovery parses the original snapshot and repeats original signature/permission verification before reading fees; it makes no current-account lookup. Independently supplied original-account overload remains available but cannot contradict a persisted snapshot. The byte-address and account-aware prepared entry points share this one admission owner.
- **Trust and scope:** this is service-owned admission evidence, not a historical block-state Merkle proof. Restrict outbox read/write access; public keys/addresses/permissions can still be correlatable metadata. Do not publish the outbox or mistake public context for billing sponsorship authorization. Missing historical context is an unresolved recovery gate, never permission to replay a transaction or invent zero fees. This does not establish full Hedera query-cost coverage, a complete Cosmos final refund model, authorized live price policy or hosted V2 acceptance.

## Approved billing policy — controlled accounting integrated; production acceptance pending

The user approved netting native fees and storage rebates **within the same admitted operation**, with a minimum final charge of zero. There is no payout, carry-forward credit, or offset against another operation.

- Retain every original signed attempt and its independently verified native receipt, including charged failures and negative net fees.
- Sum fees and rebates for the operation before applying the zero floor. Do not discard negative receipts or clamp each attempt separately.
- Example in one denomination: fees 10 and rebate 3 produce charge 7. Fees 3 and rebate 10 produce charge 0, not a payout of 7.
- Another operation's costs cannot absorb the unused rebate.
- Keep denominations explicit. MIST, SUN, tinybar and Cosmos denomination amounts are not interchangeable numbers. Mixed currencies require authoritative, auditable valuation before a combined monetary charge can be established.
- An unavailable receipt, unknown outcome, absent price or unsupported payer attribution is unresolved evidence—not zero usage and not permission to release the reservation.

This approval does not itself authorize public-chain spending, paid cloud provisioning, a production deployment, a particular exchange-rate source, or a subscription allowance change.
