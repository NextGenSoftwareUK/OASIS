## Prepared storage query policy and scope boundary

`HederaStorageConfiguration.QueryPreparation` is a real provider configuration property, not a new HTTP request JSON shape. Its `HederaStorageQueryPreparation` fields are:

- `AuthorizedNodeAccountIds`: explicit distinct numeric consensus-node IDs; the configured payer must not also be a node.
- `MaxPaymentTinybars`: positive exact native-int64 ceiling for a selected paid query, including any SDK buffer. Prepared SDK quote checks and selected-payment verification both use this policy, not the mutation's `MaxFeeTinybars`.
- `MaxTransactionFeeTinybars`: separate positive native-int64 ceiling for the signed query payment transaction's network fee; this is not an observed charge.
- `MaximumRequestsPerInvocation`: default64, allowed1..512, for one SDK invocation/stream. It is NOT an API-operation total. Host reservation must cover all invocations; Core independently enforces the operation's512-attempt/8MiB evidence limits.
- `PersistenceTimeoutMs`: default10000, allowed1..30000, for bounded acknowledgement before query transport.

Prepared storage rejects missing policy before entering the operation/resolving secrets. Configuration snapshots node arrays; changing the caller's array later cannot replace authority. One scoped backend invocation owner now handles Get/List/Probe as well as Put/Delete, retaining original prices and separate query/write identities. The old mutation-only internal scope path has been removed; ordinary unprepared storage is not a fallback after rejection. No deployment policy values have been chosen or enabled automatically; do not copy synthetic fixture amounts into deployment configuration.

## Approved billing policy — controlled accounting integrated; production acceptance pending

The user approved netting native fees and storage rebates **within the same admitted operation**, with a minimum final charge of zero. There is no payout, carry-forward credit, or offset against another operation.

- Retain every original signed attempt and its independently verified native receipt, including charged failures and negative net fees.
- Sum fees and rebates for the operation before applying the zero floor. Do not discard negative receipts or clamp each attempt separately.
- Example in one denomination: fees 10 and rebate 3 produce charge 7. Fees 3 and rebate 10 produce charge 0, not a payout of 7.
- Another operation's costs cannot absorb the unused rebate.
- Keep denominations explicit. MIST, SUN, tinybar and Cosmos denomination amounts are not interchangeable numbers. Mixed currencies require authoritative, auditable valuation before a combined monetary charge can be established.
- An unavailable receipt, unknown outcome, absent price or unsupported payer attribution is unresolved evidence—not zero usage and not permission to release the reservation.

This approval does not itself authorize public-chain spending, paid cloud provisioning, a production deployment, a particular exchange-rate source, or a subscription allowance change.
