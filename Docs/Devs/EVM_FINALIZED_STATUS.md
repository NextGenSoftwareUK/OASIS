### Chain finality scope

[Arbitrum finality reference](https://developer.arbitrum.io/how-arbitrum-works/reference/finality-and-reorgs) defines finalized in terms of finalized parent-chain batch data; self-managed chains require explicit compatible finality tracking. [Arbitrum exchange checklist](https://developer.arbitrum.io/launch-arbitrum-chain/integrations/exchange-integration-checklist) distinguishes transaction execution/finality from parent-chain bridge withdrawal/dispute-window completion. ## Findings and invariant

Ethereum, Arbitrum and the shared Web3Core status methods treated a null receipt as NotFound, failed execution as Canceled, and any status1receipt as Completed without finality/canonical-block proof. Error paths could also expose enum-zero Completed. Polygon inherits Web3Core and therefore shares its behavior. A receipt observation is not authority to resubmit, and receipt inclusion is not finalized execution or bridge settlement.

Added ONE SDK-independent `EvmFinalizedStatus` component in the existing shared provider library, not another backend/environment. It validates exact32byte hash encoding, matching receipt transaction identity, explicit nonnegative block height and status0or1, an explicit finalized checkpoint, and canonical receipt block identity/height. A receipt above finality remains Pending. Final canonical status0→Failed and1→Completed. Null receipt→Pending without claiming absence/rejection. Malformed, contradictory, missing checkpoint or noncanonical evidence throws; caller retains IsError/Pending. No confirmation-count/latest-tag fallback, submission or polling loop.

Ethereum/Arbitrum/Web3Core use actual existing Nethereum receipt and block RPC clients; Polygon inherits the shared base. Thin SDK lambdas project only required typed fields into the shared logic. Finalized block RPC uses `BlockParameter.CreateFinalized()`, canonical block query uses explicit receipt height. All four providers build successfully from existing cached SDKs. Ethereum retains its existing autoactivation behavior; other providers still require activation. Hash validation/cancellation precede activation. Error results initialize Pending. Status Failed is a successfully observed failed execution, not an HTTP/API failure, so IsError need not be true.

Observation waits have linked30second deadlines/caller cancellation. Current Nethereum calls use Task.WaitAsync: this bounds caller waiting but does NOT prove the underlying HTTP request is cancelled/disposed. This transport lifecycle gap remains open; it must not be described as full I/O cancellation. Unsupported finalized-tag endpoints fail visibly; there is no silent downgrade. L2 finalized-tag semantics do NOT by themselves prove L1 settlement/challenge expiry, bridge release or fee recovery; explicit chain-specific policy/native review is required before broad completion claims.
