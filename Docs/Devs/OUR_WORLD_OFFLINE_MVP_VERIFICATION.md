## Verified implementation invariants

- The release inspector rejects every non-passing TRX outcome, not only explicit failures. `total`, `executed` and
  `passed` must be identical, while failed, error, timeout, aborted, inconclusive, not-runnable, not-executed,
  disconnected, warning, passed-but-run-aborted, in-progress and pending counters must all be zero. This prevents a
  skipped or partially executed suite from being presented as release evidence. An adversarial validation with an
  injected warning and a passed/executed mismatch was rejected by this exact gate.

- OGEngineClient owns the reusable Edge Runtime integration. Managed/Unity offline synchronization is enabled by
  default and can be explicitly disabled; the native ABI adds versioned Edge configuration/status structures without
  changing the original configuration layout.
- Authentication requests no longer serialize anonymous objects through reflection. HyperDrive grants, exchanges,
  results, built-in projections, and command payloads use generated `System.Text.Json` metadata. Opaque world content
  remains JSON (`JObject`/`JArray`), and applications must supply generated metadata for additional typed entities.
- Windows protected offline grants use the same generated HyperDrive wire contract as macOS/Linux adapters. The
  NativeAOT build check now fails if IL2026 or IL3050 returns in authentication, synchronization, secure-grant,
  Edge-payload, or callback-marshalling files.
- Runtime tests cover validated device-bound grants, offline startup, network loss, durable local commit, process
  restart, reconnect, bounded drain, idempotent replay, stale in-flight responses, suspend/resume, and the exact
  offline/reconnecting/synchronized notification sequence.
- Quest-progress, inventory-grant, GeoNFT-collection and GeoHotSpot-trigger commands are each verified to survive
  runtime reconstruction as exactly one durable intent with unchanged operation, entity and command identities.
  Offline initialization hydrates the tracker pending count from SQLite before publishing status, so a restarted
  client cannot briefly report zero while durable work is waiting.

## Hosted Atlas tier, capacity, and failover constraint

The production-configured `OASIS` cluster was inspected in Atlas on 2026-09-25. It is an AWS N. Virginia
(`us-east-1`) Free cluster running MongoDB 8.0 with a fixed three-node replica set. Atlas showed 37.2 MB of logical

MongoDB's documented Free-cluster limits at the time of verification are:

| Resource or capability | Free-cluster limit |
|---|---:|
| Data plus indexes | 512 MB total |
| Read/write throughput | 100 operations per second |
| Concurrent connections | 500 |
| Data transfer | 10 GB in and 10 GB out per rolling seven days |
| Databases | 100 |
| Collections | 500 total |
| Free clusters | One per Atlas project |
| Replica set | Three nodes, managed by Atlas |
| Database-name length | 38 bytes |
| Namespace length | 95 bytes |
| In-memory sort | 32 MB |
| Aggregation pipeline | 50 stages |

Free clusters do not provide automated backups, configurable storage or memory, sharding, private endpoints,
network peering, downloadable database logs, manual primary-failover testing, or regional-outage testing. They do
not honor `allowDiskUse` for temporary aggregation files and can be automatically paused after 30 days with no
connections. The authoritative list is MongoDB's
[Atlas Free Cluster Limits](https://www.mongodb.com/docs/atlas/reference/free-shared-limitations/).

Atlas-managed primary-failover testing requires a dedicated M10-or-higher cluster. On 2026-09-25 MongoDB listed an
AWS `us-east-1` M10 with its default 10 GB storage at USD $0.08 per hour, approximately $56.94 for continuous monthly
use. Dedicated clusters are billed hourly while active; storage, backup, data transfer, and optional features can
add charges. A temporary M10 used for one to three hours would therefore have approximately $0.08-$0.24 in base
compute cost, and it must be deleted after testing to stop further compute charges. Current prices must be confirmed
in Atlas before creation; see [Atlas AWS pricing](https://www.mongodb.com/products/platform/atlas-cloud-providers/aws/pricing)
and [Atlas billing](https://www.mongodb.com/docs/atlas/billing/).

## External release gates

The current aggregate gate requires both the hosted Mongo transaction suite and a separately coordinated abrupt
primary-process-loss TRX. The portable Windows evidence runner and the independent Linux CI job each use a real
three-member MongoDB replica set, terminate the elected primary, wait for a new election, and prove acknowledged
replay. An Atlas M10-or-higher failover exercise remains valuable production soak evidence, but it is no longer
misstated as the only way to prove the provider's transaction/election invariant.

A physical Android device remains required to verify first online sign-in, flight-mode startup, process kill/restart,
radio loss/recovery, frame-time percentiles, memory, database growth, network use, battery/thermal behavior, and
hardware-backed credential behavior. On 2026-10-03 a read-only Railway production audit confirmed that both
`OASIS_OFFLINE_GRANT_SIGNING_PRIVATE_KEY` and `OASIS_OFFLINE_GRANT_SIGNING_PUBLIC_KEY` are populated on production
WEB4, without printing either value. The public key embedded in
`artifacts/our-world-release/omniverse_host_config.production.json` exactly matches the deployed production public
key. A live unauthenticated request to
`https://api.web4.oasisomniverse.one/api/hyperdrive/sync/offline-session-grant` returned HTTP 401, proving the route
exists behind the expected authentication boundary rather than returning 404 or disabled-service status. Issuance,
signature validation, renewal and revocation with a real production identity still require an explicitly designated
production release-test avatar or bearer token; no ad-hoc production account is created by the release process. A
Google Play Console application and its publisher access remain required for store submission.

Physical qualification is now a machine-enforced release input rather than an informal sign-off. Start with
`Scripts/our-world-device-acceptance-evidence.template.json`, retain the raw profiler, device-log, screenshot/video
and synchronization records beside that document, and record each relative path with its SHA-256 digest. Run
`Scripts/validate_our_world_device_acceptance.ps1 -EvidencePath <completed-json>` to verify all 13 Android, iOS and
two-device Holochain cases, device/build identity, evidence hashes, and the measured resource values against the
explicit budgets recorded for that run. A production candidate can require this evidence by passing both
`-PhysicalDeviceEvidence <completed-json>` and `-RequirePhysicalDeviceEvidence` to
`Scripts/validate_edge_runtime_release.ps1`. The release gate validates the source commit, packages the raw evidence,
and incorporates both its validation result and ZIP into the checksum and signed-provenance set. The template itself
does not constitute evidence and every `PENDING` case fails validation. Evidence schema v2 explicitly requires
p95 CPU utilization and synchronization-drain latency (with positive budgets) in addition to frame time, peak PSS,
database growth, reconnect latency, battery drain and network transfer. This prevents an apparently complete mobile
qualification from omitting the CPU cost or the time required to finish reconciliation after connectivity returns.
`Scripts/test_our_world_device_acceptance_validator.ps1` is part of the aggregate release gate and proves the
validator accepts a complete portable fixture while rejecting a changed hash, exceeded frame/CPU budgets, a missing
sync-drain measurement and a missing required case.

For the Android/Holochain portion, `Scripts/start_our_world_android_qualification.ps1` is the fail-closed setup
entry point. It locates the Android SDK supplied by Unity or a normal Android SDK installation, requires two
authorized non-emulator ARM64 devices, records immutable device/build identity and pre-run battery/memory evidence,
and can install the exact APK on both devices with `-Install`. It deliberately leaves qualification status as
`PENDING`: inventory, installation, an emulator, or a successful player build cannot be converted into physical
acceptance evidence. Example:

```powershell
Scripts/start_our_world_android_qualification.ps1 `
  -ApkPath artifacts/our-world-release/OurWorld-Edge-Android.apk `
  -Install
```
