## ActivityPub cross-instance read acceptance

Development e247ea434af1 includes the native-qualified public URI route. A separate native regression on the provider branch verified that reading the exact URI after native deletion returns RecordNotFound in both entry points. The first Development rollout check showed all seven APIs pending. [Native absence evidence](https://github.com/NextGenSoftwareUK/OASIS/actions/runs/43486323641/job/132095639208).

The shipping provider-key route resolved a public object URI on the configured Mastodon instance in both sync and async modes. Both cases confirmed exact object identity, the instance-local status ID and HyperDrive serving-provider attribution. The public and private fixture deletions were independently confirmed. [Native Mastodon job](https://github.com/NextGenSoftwareUK/OASIS/actions/runs/43484054336/job/132087695900).

Mastodon status and account IDs belong to the instance that returned them. Cross-instance status reads need an explicit ActivityPub object URI and an exact match against the returned status URI. Mastodon's authenticated search can resolve an HTTPS URL. That lookup uses the configured instance and its read-scoped token. [Native ID scope](https://docs.joinmastodon.org/client/public/) · [URL resolution](https://docs.joinmastodon.org/methods/search/)

The current HyperDrive provider registry selects by provider type, so two ActivityPub instances need distinct configured identities in the routing layer before they can be independent candidates. A native acceptance fixture should use two instances with different local IDs for the same public object. Verify exact URI and serving-instance attribution during normal selection and during an outage of the first reader, including rejection of unrelated search results. The existing private-status read and delete evidence applies to the originating instance. [Exact Development CI](https://github.com/NextGenSoftwareUK/OASIS/actions/runs/43449954359) also verified exact public object resolution, instance-local status ID and independent HTTP 404 after fixture deletion on one Mastodon instance.

The Core audit found three places where instance identity must travel together. Registration rejects a second provider of the same type. Selection and attempted-provider tracking use the provider type, as do health metrics and response attribution. A future instance-aware read must bind a configured instance through all three stages. Otherwise an outage on one instance can affect the health or attempt state of another, and the response cannot identify which instance actually served the object.

The existing router stops on authoritative record absence. An instance-aware ActivityPub route must preserve that distinction: a transport outage may advance to another enrolled instance, while a healthy response that cannot resolve the exact public object must retain its absence result. The native fixture should exercise both paths.
