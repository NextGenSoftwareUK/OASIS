# Algorand durable storage implementation scope

The shipping Algorand provider reads account and transaction data through Algod and Indexer and submits signed transactions. Its native payment and public read evidence is recorded in the [provider matrix](PROVIDER_MATRIX.md). Durable OASIS records need an application with their own ledger state and a native acceptance fixture.

## BootLoader enrollment

- Configure `OASIS.StorageProviders.AlgorandOASIS` with the Algod and Indexer origins for the same ledger. An explicit empty entry uses the public mainnet origins. Operator endpoints can use HTTPS, and disposable local fixtures can use loopback HTTP. A request-time endpoint override cannot redirect this paired configuration.
- For authenticated nodes, set `AlgodTokenEnvironmentVariable` and `IndexerTokenEnvironmentVariable` to the names of the operator-managed environment variables. Omitting a name sends no corresponding token.
- For encrypted holons, configure `RecordStorage` with `ApplicationId`, `GenesisHash`, `WriterAddress`, `ApprovalProgramSha256`, and `StorageKeyEnvironmentVariable`. Its named environment variable must contain the Base64-encoded 32-byte encryption key. Name `WriterSeedEnvironmentVariable` only for a signing host. Its value is the Base64-encoded 32-byte seed for the enrolled writer. The default `MaximumFee` is 1,000 microALGO per native transaction.
- Warm registration defers network calls to activation. The `storage_bootloader` hosted LocalNet case exercises that registration, activation of the same provider instance, and signed standard holon save and read.

The [exact Development qualification](https://github.com/NextGenSoftwareUK/OASIS/actions/runs/43753371692) passed one native case with zero skips in 391 ms and verified LocalNet container, network, volume and fixture teardown. f50a2a48dde8 includes the registration path on Development. This case exercises registration and storage with automatic routing disabled.

## Ledger contract

Avatar details use a distinct kind inside the opaque key and encryption context. Their encrypted discovery descriptor carries that kind and the OASIS ID. Ordinary holon descriptors retain the ID-only encoding, and holon discovery validates all descriptors while returning the ordinary holon identities. An avatar-detail update requires its exact predecessor revision ID as well as the version number. The [native same-ID and history case](https://github.com/NextGenSoftwareUK/OASIS/actions/runs/43754674014) is qualifying.

The initial native publication reached the existing transaction size bound. Profile records now use the existing compressed encrypted envelope, subject to the same on-chain size limit and the codec's decompression limit. The [replacement fixture](https://github.com/NextGenSoftwareUK/OASIS/actions/runs/43755287511) also tests empty, current, historical and missing-version profile lists. Collection discovery reads payloads only for the requested kind and limits concurrent record reads.

- Bind the store to the Algod genesis hash, application ID, verified approval program and expected writer address. Confirm the same identity before loading or publishing any record.
- Keep one manifest box per opaque record key. Derive the key from the store secret, record kind and OASIS ID. Encrypt payloads and any private metadata with the existing `EncryptedRecordCodec`, using the store and record identity as authenticated context.
- Stage larger encrypted payloads in bounded revision boxes. The owning application publishes a manifest only after verifying the authorized writer, the expected predecessor and all required chunks. Readers resolve the manifest and verify its payload digest and authenticated envelope. Unpublished chunks remain eligible for explicit cleanup by revision.
- Check the current manifest inside the application before creating, replacing or tombstoning it. Preserve published predecessor references for versioned reads. Treat an acknowledged hard delete as removal of the current and historical payloads in the application state, subject to the chain's public transaction history. Design the encrypted application-call arguments with that permanent history in mind.
- Report an unsupported record size or insufficient application funding before dispatch where the limit is knowable. Use the application account's native minimum-balance requirement and the transaction's current box reference and argument budgets.

The Algod box endpoint supplies the exact native key, value and confirmed round for independent readback. Application boxes are readable off chain. Every application transaction must keep private fields inside an authenticated envelope. [Algorand box storage](https://dev.algorand.co/concepts/smart-contracts/storage/box/) · [Algod box lookup](https://dev.algorand.co/reference/rest-api/algod/operations/getapplicationboxbyname/)

## Acceptance order

1. Use the existing authenticated LocalNet fixture to deploy and fund the exact contract. Verify program identity, authorized writes and a wrong-writer rejection.
2. Publish and read an encrypted holon through the shipping provider, independently verify the native box, and verify a conflicting revision fails without changing the head. Exercise chunk admission and a fresh client after process restart.
3. Qualify lookup, collection enumeration, version history and deletion through the shared storage contract before enrolling the provider in storage routing. Exercise avatar and avatar-detail capabilities with the same private-store semantics.
4. Preserve actual transaction receipts and native box digests as compact evidence. Release the fixture application and its boxes on the owned LocalNet. The funded public TestNet action already lives in [Actions for David](../Release%20and%20Status/ACTIONS-FOR-DAVID.md).

Revision 27283cfbf8e0 freezes the exact head, removes discovery, and persists a native purge checkpoint. The contract removes one published manifest and its chunks per transaction and advances to its authenticated predecessor. A terminal fence prevents ID reuse. The [first hard-delete qualification](https://github.com/NextGenSoftwareUK/OASIS/actions/runs/43744368454) stopped before deletion when publication exceeded the single-call opcode budget. Historical transaction bytes remain on the chain.

Revision e73efef5a3f3 collects chunk staging and publication in one signed Algorand transaction group. The contract requires each stage to bind the final publish call's writer, record key and revision, and validates its position against the chunk index. Algorand pools the opcode budget across the group and applies all calls together.
