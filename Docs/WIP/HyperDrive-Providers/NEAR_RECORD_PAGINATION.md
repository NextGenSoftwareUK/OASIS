## Root cause

The retained custom contract's `entries` used `records.toArray().filter(...)`. Filtering after materializing every encrypted record exhausted view gas as the retained ledger grew. Four storage tests failed with GasLimitExceeded. Resetting the ledger, deleting unknown records, increasing gas or returning a partial result would not fix enumeration scalability/correctness.

## Contract and SDK change

New `entries_page(prefix,offset,limit)` uses actual near-sdk-js2.0.0 `UnorderedMap.keys({start,limit})` bounded vector access, then reads values only for matching keys. Maximum64scanned keys; provider requests16. Response carries total collection length, next_offset and matching rows. Offset/limit validation rejects malformed/out-of-range requests. Collection field names/prefixes and initialization stay unchanged; no state migration/reset is intended. Legacy entries remains an old ABI method but provider enumeration no longer invokes it.

The real near-api-js7.3.1 bridge pins a finalized block hash with viewBlock and supplies that SAME blockId to every callFunction page. This prevents map swap-removal/insertions between pages from skipping or duplicating records. Empty filtered pages must still follow continuation. Snapshot pruning/errors propagate; no latest-state fallback/restart. Reject changed totals, invalid continuation, duplicate/out-of-prefix/malformed rows. Bounded100000scanned records and64MiB collected UTF-8 payload; exceeding a bound is an explicit error, never successful truncation. No partial result returned on any page failure. Node helper is copied alongside the bridge for build/publish.
