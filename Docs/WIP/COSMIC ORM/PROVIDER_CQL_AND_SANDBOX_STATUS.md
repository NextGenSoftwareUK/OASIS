## What each CQL level means

| Level | Implemented/proven scope | Limits |
|---|---|---|

Native capability rejection is not feature support. |
| Bounded source CQL | Explicit native key equality/membership over configured records; three-record query/two-key subset; immutable mapped holon IDs/provenance; visitor-owned two-record Mongo snapshots; paired five/four physical rows; access isolation | Not arbitrary source scans, full text/search, arbitrary Name/Description/metadata filtering, general aggregation/joins, owned on-chain persistence or full ORM. Query capabilities define the exact contract. |
| Azure local subset | Parameterized native row predicates: canonical fields, string/Boolean metadata, Boolean composition, null/existence, membership, supported ordering/paging; projection and Count/LongCount/Any implementations present; emulator/native evidence retained | No hosted Azure acceptance; no equal-depth three-store parity certification. Earlier audit gates are historical, not a current comprehensive feature matrix. |
| Oracle bounded canonical subset | Bounded ID equality/membership; Name/Description equality or substring; string metadata equality, Boolean combinations and paging over authoritative catalogue; native local HTTP/Mongo pairing verified | No hosted Oracle; use orderBy None; sorting, full graph loading and full EF parity not enrolled. |
| Not CQL-certified here | Underlying provider implementation/SDK/storage evidence may exist, as recorded per row below | Do not call these fully CQL implemented or sandbox ready merely because SDK/CRUD exists. |
