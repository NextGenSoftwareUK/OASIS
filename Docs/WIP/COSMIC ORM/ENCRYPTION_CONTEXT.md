## Next implementation contract: durable key identity

This section is a design, not shipped support. Use one versioned metadata envelope containing a format version, opaque key/context ID, algorithm ID, nonce, authentication tag and ciphertext. Never persist encryption settings or key material. Bind the envelope to logical record identity and trusted tenant/context identity through authenticated associated data; provider identity must not invalidate byte-preserving replication. Stored key references are untrusted selectors, not authorization.

A runtime-owned resolver must authorize that reference using trusted execution context and return owned key material with a defined disposal lifetime. New writes need an explicit configured key identity and crypto policy captured in the save plan. Reads choose a declared format and authorized key reference; they must not trial-decrypt across keys or silently retry another provider. Rotation creates new conditional revisions and retains the explicit key lineage needed for retained history and original receipts.

Existing `r256:`/`qpq:` payloads have no persisted key reference. Their V2 data-format migration needs explicit operator policy and verification; current runtime configuration must not be advertised as historical key discovery. The current CBC layer does not authenticate its ciphertext, and the `QuantumEncryption` setting names an AES-GCM layer rather than a post-quantum public-key protocol. A new envelope must use authenticated encryption and test identity/context tampering, copied ciphertext, retired/unavailable keys and deterministic authorization failures. Resolver admission must be propagated through CRUD, child graphs, history, replay, replication and migration before closing this gate.

### Protocol and integration details

The immutable policy is configured with `new HolonMetadataEncryptionPolicy(contextId, writeKeyId, authorizedResolver, additionalQueryableKeys)`. Its `IHolonMetadataKeyResolver.ResolveKey` returns `OASISResult<HolonMetadataKeyMaterial>` and receives record ID, context ID, stored/selected key ID and Encrypt/Decrypt purpose. The resolver belongs to a trusted runtime authorization scope. It must return a fresh owned lease; the cipher disposes and zeroes that lease, and also zeroes temporary plaintext byte buffers. The original byte array supplied to a key lease is cloned, not mutated. No vault implementation, user authentication system or key distribution service is implied by this interface.

The writer uses the selected current key ID; the reader uses the envelope's retained key ID after validating the expected record and trusted context. Changing a policy alone does not dirty an unchanged entity or migrate stored data. Native rotation evidence covers an actual edited write selecting the new key and an independently created manager retaining access to older keys. Mixed key IDs within one context are verified after restart; mixed context IDs still require explicit authorized runtime context selection and are not certified as automatic cross-tenant graph reads.
