# Typed child collection ownership

Checkpoint: 20 October 2026. Implementation and verification remain in progress.

COSMIC tracking now captures explicitly declared child collections rather than treating `Children` as the complete semantic graph. `ICosmicChildCollections` and `HolonChildCollection` describe stable collection names, immutable membership snapshots and local membership restoration callbacks. Capture validates that declared members match `AllChildren`; undeclared semantic members fail explicitly. Moving a child between roles is dirty even when flattened child order stays unchanged.

Tracking, reject planning and save planning share this captured membership. Successful save publication accepts the submitted collection snapshot, preserving changes made by the caller while I/O is pending. Manager preparation traverses the staged `Children` graph, which already contains the selected semantic members. Shared graph write planning uses the same capture contract.

STAR declares celestial-space body/space memberships, body-core zomes and delegated body-core children. Celestial-space restore preserves existing readonly list views, detaches handlers from pending members and attaches handlers to restored members. This restores local subscriptions without performing provider operations.

Body `AllChildren` now includes independent body-owned physical children alongside core-owned children/zomes. If body and core reference the same physical list, that list has one membership owner; the core binding restores its alias after physical membership restoration. This is reference-identity ownership, not ID-based deduplication that could hide invalid duplicate graph nodes.

Graph acceptance now prepares all selected membership captures, serialized values, compatibility `Original` views and comparisons before publishing any baseline. An invalid descendant therefore cannot mark an unaccepted ancestor as accepted. This is validation/materialization ordering, not a claim of thread-safe concurrent mutation or transactional arbitrary user property setters.

Manager batch-load tracking uses the same preparation pass across all returned roots. A later invalid record cannot accept an earlier new record or overwrite its previous private baseline. Shared graph references are visited once across the result rather than independently for each root.

Save acknowledgement validation rejects null records and requires the complete acknowledged identity set to equal the submitted selection before caller publication. Extra records cannot silently expand the acknowledged graph. Existing empty/duplicate identity and missing-selection checks remain enforced.

The save plan also retains explicit parent identities and allocated selected-child parent edges independently of mutable staged records. Conflicting acknowledged parents fail before publication. An unspecified root parent is outside this particular check: manager preparation assigns its creation owner, so fully binding that default requires capturing intent after preparation and before provider submission. This remains an open boundary rather than a claim of complete parent-intent validation.

V2 follow-on closes that preparation boundary for the normal single/batch preparation routes: detached staged nodes are associated with their owning plan, and prepared parent identities are captured after audit preparation and before routing. Subsequent acknowledgements must preserve these identities, including an empty prepared parent. Repeated preparation cannot change an already captured parent. Associations are removed on plan disposal. Legacy paths are not enrolled in this new preparation hook. Transfer/delete and native provider coverage must still be verified separately before universal certification.

## Open acceptance criteria

Encryption ownership follow-on: save preparation snapshots effective per-holon/global metadata encryption settings on the detached value; acknowledgment materialization carries that context into decryption. Decryption now honors a per-holon override. Two sync/async tests mutate the caller override key during provider I/O and require successful submitted-value publication. Both first failed (`encryption-context-before.trx`); final Core1,126/1,126 passes (`encryption-context-core-current.trx`), both targets build. This fixes process-local save publication, not durable key identification/rotation or generic provider-load decryption context; those remain open.

Expanded encryption-context verification: the same sync/async cases now cover both per-holon overrides and global settings mutated during provider I/O. Full Core1,128/1,128 passes (`encryption-context-expanded-current.trx`). No additional producer changes were needed. The detached settings snapshot owns acknowledged-save decryption for either configuration source; generic later loads and durable key versions still require a separate persisted key-context contract.

See [durable child role implementation boundary](DURABLE_CHILD_ROLE_PLAN.md) for the required manifest, binding and partial-hydration invariants.

These tests do not certify durable role reconstruction after loading generic provider records. A persistent relationship-role contract and hydration rules remain necessary. Mongo/Neo native typed-graph saving, provider-I/O membership ownership, native depth/scope combinations, native STAR body/core persistence and provider-loaded reconstruction require further verification. All other roadmap items, including migrations, committed deltas and CQL, remain tracked by the main roadmap; this checkpoint does not close them.
