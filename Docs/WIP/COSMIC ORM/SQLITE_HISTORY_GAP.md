# SQLite holon history: implementation and remaining gaps

20 October 2026. Current implementation: opt-in atomic archive capture covers ordinary saves/deletes, conditional mutations and committed replica replacement. Checksum-validated historical point/key/collection/parent reads are implemented, including concurrent rollover and conflicting-revision checks. Latest completed full suite is797/797, zero skipped (`metadata-query-sqlite-verified.trx`); owned database/wal/shm absent after terminal completion. Selected holon metadata/search history routes are verified below; broader query coverage, retention/restore policy, typed role hydration and broader acceptance remain open. This is not a legacy-only exclusion.

## Original findings (before the implementation checkpoints below)

`HolonRepository.Get/GetAsync` query the current `Holons` table with `(version == 0 || row.Version == version)`. `AddOrUpdateHolon` finds a single row by public ID and replaces its scalar values. The selected adapter has no holon revision archive entity/migration or archive read owner. `SqliteReadVersion.Validate` checks only nonnegative input; positive input does not establish historical retrieval capability.

Consequently, an old version stops being available after the row advances. Logical `VersionId`/`PreviousVersionId` lineage and durable operation receipt replay do not supply arbitrary historical record reads. Existing receipt tests prove original acknowledged snapshots for known operation IDs, not the versioned load API. Earlier SQLite depth/role/state verification must not be interpreted as history certification.
