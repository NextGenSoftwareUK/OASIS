# Durable child roles: implementation boundary

20 October 2026. This is an implementation plan, not a completed capability.

The data-contract prerequisite is now implemented in Core: `HolonChildRoleManifest` schema1, immutable `HolonChildRole` entries and `HolonChildCollectionState.CreateManifest(parentId, identityResolver)`. Roles serialize in ordinal name order while child order is retained. The resolver can supply allocated save-plan IDs without mutating caller entities. Duplicate role names, empty identities, self-parenting and a child owned by multiple roles are rejected. Unobserved collection state cannot emit a manifest. This contract is not yet attached to provider records or save requests.

Verification: both Core targets build; full Core1,107/1,107 passes, zero skipped (`TestResults/CosmicMongoCurrent/role-manifest-core-current.trx`). Six cases cover detached immutable inputs, canonical serialization round-trip, planned identities without caller publication, unobserved membership and ambiguous ownership. Provider persistence, strict wire parsing, size bounds, hydration and migration remain unimplemented for this manifest.

Wire follow-on: `HolonChildRoleManifestJson` now writes canonical schema1 fields (`schemaVersion`, `parentId`, `roles`, role `name`/`childIds`) and validates exact fields/types, duplicate properties, supported versions, canonical nonempty lowercase GUID-D strings and trailing data. Roles are bounded at256 and total child links at65,536; wire input is bounded at8,388,608 .NET string characters and JSON depth16. These are explicit initial contract limits, not provider capacity claims. Both Core targets build; full Core1,116/1,116 passes (`role-wire-core-current.trx`) with nine new canonical-byte/rejection cases. The above unimplemented wire/bounds items are superseded by this checkpoint; provider enrollment, persistence and hydration remain open.

The current local collection contract captures membership and restoration callbacks. `StoredRecordJson.IsNavigationMember` excludes holon references and collections from canonical scalar records. Shared `HolonGraphWritePlan` records selected child IDs but flattens role distinctions. Native provider loads consequently reconstruct the physical graph, not the caller's typed collection roles. The SQLite typed-save tests prove selected members are stored, not that typed roles round-trip.

## Required invariant

Save-plan integration checkpoint: `HolonSavePlan` now builds immutable role manifests after all selected graph identities are allocated. Manifests are keyed by parent planned ID and retain submitted membership even when callers edit collections later. Only nodes whose child collections are selected emit manifests; a root-only or depth-excluded collection emits none, preserving the distinction between an empty selected collection and unobserved membership. Provider requests do not yet consume these manifests. Core1,118/1,118 passes (`role-plan-core-current.trx`), including two new save-plan integration cases; both targets build.

Consumer verification: actual STAR8/8 (`role-plan-star-current.trx`) and SQLite native709/709 (`role-plan-sqlite-current.trx`) pass with the latest Core planning/prepared-parent/batch-tracking changes. The authoritative parent revision must own an immutable ordered relationship manifest. Each entry identifies a stable role and ordered child IDs. Membership removal means unlinking; deletion remains an explicit operation. A provider cannot acknowledge a role-aware write while discarding its role manifest.

Resolution prerequisite implemented: `HolonChildRoleResolution.Resolve` accepts a fully selected manifest and a loaded-record resolver, validates every returned ID and parent ID, and returns immutable role lists holding the actual loaded references in manifest order. 1. Add an explicit versioned data contract for relationship manifests, distinct from executable local restoration callbacks. Validate names, duplicate roles, empty IDs, duplicate graph membership, maximum bounds and canonical ordering before provider I/O.
2. Bind manifest child IDs after save-plan identity allocation. Keep excluded collections at their accepted or stored state; a depth-limited save must not replace unselected relationships with an empty list. Define new-root behavior when descendants were never submitted.
3. Persist the manifest with the parent conditional commit, operation receipt, history and replication intent. Include it in canonical request hashing and replay checks. Preserve it in every certified provider DTO/mapper; unsupported providers must report the capability explicitly.
4. Hydrate selected records first, validate stored manifest references against the requested visibility/depth boundary, then restore registered local roles. Distinguish an unhydrated member from a corrupt missing reference. Do not invoke callbacks supplied by stored data or resolve arbitrary runtime types from role names.
5. Supply explicit role-binding APIs for empty runtime collections. The existing captured callback restores a particular snapshot; it cannot be repurposed as a general loader for arbitrary stored membership. STAR body/core alias roles require one physical membership owner and deliberate alias restoration.
6. Accept tracking only after successful graph materialization. Preserve stored relationship state separately from the partially hydrated runtime view so later partial saves cannot erase unobserved members.
